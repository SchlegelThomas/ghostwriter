Ghostwriter delivery plan · Writing and agents epic

Capture to Story

Let writers capture prose, voice, images, audio, and files from anywhere in a project, then use bounded agents to help turn that material into a coherent story without forcing structure before inspiration or silently changing canon.

Status: active — founder accepted plan and implementation 2026-07-24; checkpoint delivery underway
Branch: feat/capture-to-story-agents
Owner: founder + parent agent
Living designs: Mockups 2.0 · Mockups 3.0 · Mockups 4.0 · Mockups 5.0 · Capture to Story

Intent

Make capture—not hierarchy—the easiest way into Ghostwriter. A writer can open Capture from Project, Draft, Canvas, or a narrow screen and begin immediately. The original material is durably acknowledged into a project Inbox as an explicitly noncanonical artifact; the writer does not need to choose a book, chapter, scene, Canvas position, or craft framework first.

After an acknowledged pause, Ghostwriter may quietly offer Help find its place. That invitation never starts a provider call by itself. When the writer accepts, a bounded agent receives an inspectable context receipt and returns durable, revision-bound proposals: create or place a scene, make a scene variant, shape a sketch, update a character sheet, add a backdrop constraint, or connect the material to Canvas. The writer compares and applies an exact proposal; the core rechecks all versions and either applies the complete change or nothing.

This epic also establishes OpenAI as the first bring-your-own-key provider, with each writer's key encrypted server-side and never returned after storage. External MCP clients may read granted context and create proposals, but cannot apply them.

AI onboarding is progressive rather than a prerequisite: Capture remains immediately available, and provider setup appears only when the writer first requests agent help. Writers may optionally define collaboration preferences, project instructions, and declarative agent playbooks. These are lower-trust guidance layers—not executable code, new tools, or authority—and the effective instruction stack is visible before egress.

Explicitly out of scope: generic always-on project chat, autonomous background agents, automatic story placement, silent prose edits, open-web research, OCR or managed audio transcription, arbitrary file parsing, same-scene collaborative editing, Guided/Balanced/Minimal onboarding, full project import/export, and a second canonical manuscript store.

Founder revision 2026-07-25: Scene Partner is a job-bound conversational agent (not generic chat). It shows thinking, scans manuscript scenes for matches, interviews when unclear, iterates prose with the writer, and may propose scene images. Apply remains human-gated. Generated images for Scene Partner are now in scope for this epic.

Product thesis and authority

  • Capture first: inspiration can precede structure. Capture is always reachable and never begins with a setup form.
  • Preserve the original: integration creates an attributable story artifact while retaining the source capture and its exact applied revision.
  • One story model: accepted prose still lives in canonical scene documents; Canvas cards still reference the same scene IDs; Capture is a noncanonical Inbox source, not another manuscript.
  • Guidance is optional: the quiet integration invitation appears after an acknowledged pause and can be dismissed indefinitely. No provider egress occurs until the writer explicitly starts a workflow.
  • Setup follows value: publishing profile and AI configuration never gate Capture. Provider connection and optional collaboration preferences appear just in time at the first agent request.
  • Agents have jobs: Scene Partner integrates prose, Sketch Partner shapes intent, Character Coach sharpens agency, and Worldkeeper connects place and consequence. Conversation is supporting context, not the artifact.
  • Propose is not apply: model output cannot create a canonical revision event. A human approval bound to a proposal hash and current revisions is required.

Acceptance criteria

  1. From Project, Draft, Canvas, and narrow web, a signed-in writer can open Capture, type or dictate immediately, and receive truthful Saving, Saved, Not saved, conflict, and recovery states without first creating manuscript structure.
  2. A capture supports scene-compatible rich prose and bounded image, recorded-audio, and file attachments. Text promotes losslessly; binary objects remain authenticated references and never enter Postgres or the ProseMirror document.
  3. Captures persist in a project Inbox with stable IDs, current version, revisions, attachment status, provenance, and clear Draft / ready / integrated / archived states. Refreshing or changing devices does not lose acknowledged work.
  4. The original capture remains inspectable after integration. The applied target records the capture revision and proposal that produced it; later edits do not create two competing canonical scene bodies.
  5. Without AI, a writer can explicitly turn a capture into a new unassigned or placed scene and optionally place the same scene on Canvas in one acknowledged operation. Version conflict changes nothing.
  6. After an acknowledged pause, the Inbox may show a quiet Help find its place invitation. Dismissal is durable enough not to nag; the invitation never triggers network egress or consumes provider budget.
  7. A writer can add, test, rotate, and delete an OpenAI key. The key is encrypted server-side per account, never returned to a client, never logged or exported, and provider failure leaves captures and canonical story state unchanged.
  8. A writer can skip AI setup, capture without a provider, and complete provider setup only when first requesting help. Publishing identity, legal/contact, mailing, biography, and representation fields are excluded from model context unless a future workflow obtains separate explicit consent.
  9. A writer can define account collaboration preferences, project instructions, and versioned declarative playbooks with explicit trigger, context scope, output type, and guidance. The run receipt previews the effective instruction layers; user content cannot add tools, grant permissions, expand egress, override proposal-only authority, or cross project boundaries.
  10. Every real agent run shows the approved resources, exact revisions, destination, budget, provider, and model before egress. Context is assembled server-side; client-supplied prose or IDs cannot broaden scope.
  11. Agent runs and proposals survive refresh and expose queued, running, needs-input, ready, failed, canceled, stale, rejected, and applied states where applicable. Errors contain no manuscript text or credentials.
  12. Scene Partner can propose at least two labeled outcomes against an immutable base: create a new scene from a capture or create a named variant of an existing scene. The working draft stays unchanged until a separate writer apply action.
  13. Sketch Partner, Character Coach, and Worldkeeper use the same receipt and proposal pipeline for typed craft deltas. Their output cannot enter scene prose unless the writer chooses a prose workflow.
  14. An integration proposal can place or link the resulting canonical scene on Canvas while preserving manuscript-order authority. Draft, Canvas, Inbox, history, and Split use the same scene ID after acknowledgement.
  15. Stale capture, scene, project, or Canvas versions make the proposal stale or conflicted and apply nothing. Retry or rebase creates a new proposal; it never rewrites provenance.
  16. A project-scoped MCP grant can read explicitly granted captures/context and submit typed proposals. External clients cannot apply proposals, retrieve provider credentials, enumerate unauthorized projects, or widen their own grant.
  17. All wide and narrow workflows have keyboard and screen-reader paths, deterministic focus transfer, reduced-motion behavior, bounded payloads, and useful empty/loading/refusal states.

Domain and design audit

Canonical objects and version domains

  • Capture: project-owned noncanonical rich document with its own CaptureId, working version, immutable revisions/content hashes, status, author, timestamps, and optional source modality.
  • Capture attachment: Postgres metadata plus an authenticated object-store key, content type, byte size, checksum, processing state, and deletion state. Raw bytes never live in project rows, prompts, logs, or exports by default.
  • Inbox item: a projection over captures, agent runs, and proposals—not a second content owner.
  • Context receipt: immutable authorized resource revisions, inclusion reasons, sensitivity/egress classification, size budget, provider destination, and hash.
  • Agent run and proposal: initiator, workflow version, provider/model, receipt, exact targets/base revisions, typed payload, content hash, state, decision, and apply result.
  • Provider credential: account-owned encrypted secret envelope, provider, masked display metadata, key version, validation state, and timestamps. Decryption is confined to the backend provider adapter.
  • AI collaboration profile: optional account-level interaction preferences kept separate from publishing identity and contact data.
  • Project agent instructions and playbooks: versioned, declarative, project-scoped guidance with bounded triggers, allowed context classes, and output schemas. They never own tools or authorization.
  • Existing canonical targets: scene documents and revisions, project metadata/craft records, and Canvas board objects remain authoritative in their existing independent version domains.

State and transaction rules

  • Capture save uses a dedicated expected version and bounded browser recovery; it does not advance project.version.
  • Attachment finalize succeeds only after object checksum/type/size validation; abandoned uploads expire without producing a ready attachment.
  • Capture-to-new-scene apply checks proposal hash, capture revision, project version, and optional Canvas board version, then creates scene metadata, genesis document, optional card/link, provenance, and applied proposal atomically.
  • Capture-to-existing-scene produces a named variant against an exact scene revision. It does not splice model output into the live working document.
  • Craft proposal apply uses the existing project command version; Canvas placement uses the board version; conflicts apply nothing.
  • The server compiles non-overridable product policy → workflow contract → account preferences → project instructions → playbook → assignment. It records the resulting version/hash in the context receipt and treats manuscript, uploads, custom instructions, and external MCP content as untrusted data.

Design surfaces

  • Wide: Capture is a lightweight composer available from the persistent rail/command path without replacing the current center surface; Inbox is the durable review home; Canvas and Draft handoffs preserve selection.
  • Narrow: Capture and Inbox are first-class destinations rather than compressed desktop panes. Text, dictation, attachment progress, one proposal decision, and recovery remain usable one-handed and with assistive technology.
  • Draft and Canvas: accepting integration opens the canonical scene in Draft or Split when supported; Canvas never embeds a second prose body or silently chooses manuscript order.
  • Focus: opening and closing Capture returns focus and selection to the invoking surface; agent readiness never steals the caret.
  • Progressive setup: first agent use opens a short provider/egress path, followed by skippable collaboration preferences. Custom playbooks live in AI settings and are previewable from each run receipt rather than blocking the writing surface.

1 · Capture prose and dictation from anywhere

Writer-visible result: open Capture from Project, Draft, or Canvas, write immediately, close it, and find the acknowledged artifact in Inbox on another load.

  • Add the capture domain, memory/Postgres repositories, migration, service, API, encrypted recovery, and rich editor host.
  • Reuse the scene-compatible ProseMirror schema without treating a capture as a scene.
  • Support keyboard and browser dictation; preserve the current surface and caret on close.
  • Refuse unauthorized, oversized, stale, or conflicting saves without losing local unacknowledged prose.

2 · Inbox and deterministic story handoff

Writer-visible result: review a capture, create an unassigned or explicitly placed canonical scene, optionally add its Canvas card, and return to the same capture with an integration receipt.

  • Build the Inbox projection, filters, status language, archive/restore, and source/target provenance.
  • Add a core transactional handoff patterned after the existing Canvas scene creation service.
  • Preserve the source capture; mark the exact revision integrated only after durable acknowledgement.
  • Expose the same deterministic handoff through a core capability and document the temporary MCP exception until grants land.

3 · Mixed-media capture

Writer-visible result: attach an image, recorded-audio clip, or bounded file to a capture, see honest upload/scan/refusal state, and retrieve or delete the original through an authorized path.

  • Provision private object storage and authenticated upload/finalize/download/delete flows; keep object keys unguessable and account/project scoped.
  • Validate declared and detected type, size, checksum, filename display, and safe rendering; never execute or automatically parse uploaded content.
  • Define cleanup for abandoned uploads, archived captures, credential loss, account exit, backups, and future portable export.
  • Keep browser dictation as text input; managed transcription, OCR, and content extraction remain separate future proposals.

4 · BYOK provider and receipt-backed agent runs

Writer-visible result: securely connect an OpenAI key, preview exactly what a workflow will read and send, run or cancel it, and see a durable result or content-free failure in Inbox.

  • Create a provider-neutral AI package with OpenAI and deterministic fake adapters, structured outputs, cancellation, usage accounting, time/token/tool budgets, and content-free diagnostics.
  • Encrypt credentials server-side with versioned key wrapping; support masked status, validation, rotation, deletion, and fail-closed decryption.
  • Assemble context on the server from authorized revision-addressed resources; do not trust client-provided manuscript context.
  • Keep Capture usable without AI; present provider setup only at first agent use, then offer skippable account collaboration preferences and project-scoped instructions.
  • Persist versioned declarative playbooks and compile the fixed instruction hierarchy server-side. Show effective layers in the receipt; reject attempts to add capabilities, tools, unrestricted resources, or executable behavior.
  • Persist receipts, runs, and typed proposals; no model operation can emit a canonical revision event.

5 · Scene Partner integrates a capture

Writer-visible result (superseded 2026-07-25): original typed reflection + apply path shipped; founder feedback replaces the interstitial UX with conversational Scene Partner (checkpoint 8).

  • Offer the invitation only after acknowledged idle; dismissal never blocks writing and no background provider call occurs.
  • Show assignment, context receipt, cost/budget posture, variants, base, differences, provenance, and “Your draft has not changed.”
  • Bind approval to proposal hash and exact capture/scene/project/Canvas versions; add idempotent transactional apply and undo/history path.
  • Handle missing key, rate limit, cancellation, malformed output, stale base, conflicting versions, deleted source, and provider outage.

8 · Scene Partner conversational craft (founder revision)

Writer-visible result: choosing Scene Partner opens a chat immediately—no Help find its place / Start interstitial. The agent shows thinking, reads manuscript scenes, matches or proposes a new scene, interviews when the idea is unclear, iterates prose with the writer, and can propose a scene image. Nothing enters canon until the writer applies.

  • Remove multi-click interstitial states from Scene Partner entry.
  • Visible thinking / tool steps (scene scan, match evaluation, clarify, prose draft, image draft).
  • Back-and-forth chat turns with BYOK OpenAI; hermetic fake for local/CI.
  • Human-gated apply for scene/prose/image proposals; draft unchanged until apply.
  • Image proposals are optional, receipt-bound, and never silent canon.

6 · Craft partners without a form gauntlet

Writer-visible result: ask Sketch Partner, Character Coach, or Worldkeeper to shape captured material into editable craft deltas, then accept selected fields without entering prose or silently asserting canon.

  • Reuse one assignment/receipt/run/proposal lifecycle for all roles; role labels are workflow lenses, not separate memory owners.
  • Compare typed field deltas and apply through existing scene.update and storyKnowledge.update commands.
  • Require writer selection when a capture could refer to multiple scenes, characters, or places; never guess a canonical target.
  • Keep advice plain-language and optional so writers do not need craft vocabulary to proceed.

7 · Scoped MCP proposal parity

Writer-visible result: pair an external client to one project and allow it to inspect its grant, read selected captures/context, and submit noncanonical proposals that appear in the same Inbox.

  • Add server-created project/resource grants, revocation, egress disclosure, audit events, and non-disclosing capability discovery.
  • Expose narrow tools for context assembly and proposal submission; validate all output as untrusted typed data.
  • Do not expose provider keys, arbitrary URLs/filesystem/shell, project-wide enumeration, canonical apply, delete, or grant mutation.
  • Prove UI/MCP normalized parity for proposal creation while preserving different permission ceilings.

Tests and verification

  • Core properties: captures never become manuscript authority; model commands cannot emit canonical revisions; apply requires matching approval hash and every expected version; replay is idempotent; conflict applies nothing.
  • State machines: capture, attachment, run, and proposal transitions reject invalid, stale, duplicate, canceled, archived, and cross-project operations.
  • Storage parity: memory and Postgres contracts, migration from empty, rollback across capture-to-scene/Canvas apply, object metadata/object-store fake parity, abandoned-upload cleanup.
  • Security: account/project authorization, non-disclosure, grant matrix, credential envelope rotation/deletion, log redaction, malicious filenames/types, oversized payloads, prompt injection, cross-project IDs, revoked access, and explicit exclusion of publishing/contact profile fields from AI context.
  • Provider: deterministic fake model in required CI; structured-output corruption, timeout, cancellation, rate limit, budget exhaustion, and missing/deleted key. Live OpenAI smoke is optional and never required in CI.
  • Instruction policy: table-driven and property tests prove fixed precedence; arbitrary writer/playbook/manuscript/MCP strings cannot add a tool, resource, egress destination, permission, or canonical effect. Fuzz oversized Unicode, nested prompt-like markup, fake tool JSON, URLs, cross-project IDs, and instruction-conflict combinations.
  • Context snapshots: deterministic golden fixtures assert the exact effective policy/workflow/preference/project/playbook/assignment versions and hashes in each receipt while excluding credentials, publishing identity, legal/contact details, and unauthorized resources.
  • API: stable request/response/error contracts, upload authorization, content limits, origin checks, context assembled from server state, and no raw prose/secret diagnostics.
  • Client/UI: save/recovery queues, focus return, quiet invitation dismissal, Inbox refresh, compare/apply, stale/refusal copy, keyboard/screen-reader semantics, reduced motion, narrow layout, Capture-before-AI onboarding, skipped setup, provider reconnect, preference inheritance, playbook preview/disable/delete, and no publishing-profile leakage.
  • Browser walkthrough per checkpoint: record route, viewport, actions, successful result, refusal result, save truth, focus, and responsive behavior.
  • Repository gates: changed-file diagnostics, focused package checks, pnpm verify, git diff --check, HTML link/structure validation, and secret/artifact inspection.
  • Deferred Playwright: after explicit founder verification, audit existing journeys and add the smallest durable Capture → Inbox → apply and MCP proposal coverage; run focused first, full suite once.

Risks and decisions

Founder direction recorded

  • Capture snippets and ideas from anywhere into a durable Inbox, then promote or attach them.
  • Offer quiet integration help after an acknowledged pause; do not organize automatically.
  • Persist a minimal proposal Inbox rather than limiting results to one Assist session.
  • Use OpenAI first with writer-owned keys encrypted server-side.
  • Do not depend on ChatGPT/Codex or Claude/Anthropic first-party CLI OAuth tokens. Current standard model APIs do not expose a documented consumer delegated OAuth flow for Ghostwriter; retain a provider adapter so an official flow can replace key entry later.
  • Support scene-compatible rich prose, dictation, images, recorded audio, and files.
  • Expose scoped read/propose MCP tools; external apply is excluded.
  • Do not add a separate checkpoint for profile/AI setup. Include progressive onboarding, optional instructions/playbooks, and adversarial verification inside checkpoints 0 and 4.

Gates before implementation

  • Media cost and safety: object-store vendor, accepted MIME classes, per-object/project limits, retention, deletion, backup, and future export must be accepted before checkpoint 3.
  • Credential custody: encryption key source, envelope format, key rotation, operator access, backup/restore, and breach response must be accepted in the provider ADR before storing a real key.
  • Capture editing depth: checkpoint 0 must confirm whether capture revisions expose full history or only recovery plus integration provenance.
  • Proposal review density: checkpoint 0 must validate whether Inbox review is a center workspace, side rail, or responsive route; agent results must not become another modal maze.

Primary risks

  • A separate capture document can feel like duplicate truth unless authority, integration state, and source provenance are unmistakable.
  • Mixed media expands security, cost, retention, export, and account-exit obligations; it must not block the text-first checkpoint.
  • Encrypted BYOK is still backend custody of a sensitive credential. Weak key management would be worse than session-only keys.
  • Combining raw user instructions with internal prompts can enable injection or accidental data disclosure. The implementation must use fixed server-side authority and capability enforcement; prompt hierarchy is explanatory defense-in-depth, not the security boundary.
  • Quiet suggestions can become interruption or hidden spend. The product must prompt locally and require explicit egress consent for every run posture.
  • Agent placement can feel authoritative even when labeled proposed. Ambiguous targets must ask the writer rather than ranking silently.
  • This epic is intentionally large. Each checkpoint must remain independently demonstrable, reversible, and releasable; no horizontal “agent platform” layer counts as completion by itself.
