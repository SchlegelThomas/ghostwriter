2026-07-24 — Shipped Write and agent baseline audited

Parallel read-only audits covered the current Write implementation, core/storage/API/client/MCP bindings, Mockups 4.0, ADR 0009, and the historical agentic blueprint. The shipped product has Writing Studio chrome, scene sketches, character sheets, backdrop companions, browser dictation, deterministic four-role proposals, scene leases/history/recovery, and Canvas/Draft shared IDs.

The current agents are workflow placeholders rather than real project-aware agents. The backend trusts client-assembled assist context, proposals are ephemeral, prose Apply inserts at the caret instead of comparing against an immutable base, packages/ai does not exist, provider streaming/cancellation/usage are absent, and MCP assist remains an explicit exception. 2026-07-24 — Founder reframed the problem as capture and coherence

The founder said the current experience is too disconnected from Canvas, requires too much hierarchy before reaching prose, and does not yet feel like a tool that helps someone write well without knowing craft best practices. The desired experience is to write wherever inspiration happens and integrate that work into the story coherently.

A second journey audit confirmed the friction: an empty project has one book and no scenes; Tiptap requires a canonical scene, selection, workspace load, and lease; Canvas scene creation asks for manuscript placement before prose; Split is wide-only; and no shipped Capture/Inbox entry exists. Unassigned scenes provide a safe low-ceremony manuscript path, but they do not satisfy the selected “quick capture first, integrate later” workflow.

The plan therefore introduces a deliberately noncanonical Capture artifact and durable Inbox. It preserves one canonical scene model by promoting through revision-bound, attributable transactions rather than making Capture a second manuscript.

2026-07-24 — Founder decisions recorded

  • Entry: quick capture of snippets and ideas from anywhere, followed by promotion or attachment.
  • Integration timing: a quiet suggestion after acknowledged pause, not a pre-writing form and not automatic placement.
  • Proposal home: a minimal durable Project Inbox rather than session-only Assist state.
  • Provider: OpenAI first behind a provider-neutral interface.
  • Credentials: writer-owned API keys persisted encrypted server-side per account.
  • Capture formats: scene-compatible rich prose and dictation plus images, recorded audio, and files.
  • MCP: project-scoped read and propose tools; no external canonical apply.

The plan adds a safety interpretation to the quiet suggestion: the UI may offer help after acknowledged idle, but it does not send content or spend provider budget until the writer explicitly begins the workflow and reviews the egress posture.

2026-07-24 — Progressive AI setup and custom playbooks folded into scope

The founder directed that profile/AI setup and user-provided skills or instructions belong in the epic without becoming a separate checkpoint. Capture remains the first action. Provider setup appears only at first agent use; optional collaboration preferences, project instructions, and declarative playbooks follow progressively and never block writing.

Current official provider documentation does not expose a general consumer OAuth delegation flow that a third-party Ghostwriter web app can use for ordinary model API billing. OpenAI's ChatGPT/Codex browser OAuth and Anthropic's Claude/CLI browser login are first-party product flows; OpenAI Apps OAuth authenticates ChatGPT to an external service, and Anthropic workload identity federation targets managed workloads. The plan keeps encrypted OpenAI BYOK and forbids reuse of undocumented first-party tokens while preserving a provider adapter for a future official delegated flow.

Publishing identity is separated from AI collaboration data. Legal/contact, mailing, biography, and representation fields do not enter model context by default. Custom playbooks may name a trigger, allowed context, output type, and guidance, but cannot add tools, egress, permissions, executable code, or canonical apply authority.

The verification strategy does not rely on filtering “nefarious” wording. Server-side policy fixes instruction precedence and capability ceilings. Table/property tests and adversarial fuzz fixtures will prove that arbitrary preference, playbook, manuscript, upload, or MCP strings cannot expand tools, resources, egress, project scope, or canonical effects; deterministic receipt snapshots prove effective instruction versions/hashes and exclusion of secrets and publishing data.

Mockups 5.0 now shows Capture-before-setup, just-in-time BYOK consent, optional collaboration preferences, a custom playbook, effective-instruction preview, and the non-overridable server-policy boundary.

Feature checkpoint 0 — working notes

Outcome

  • Writer-visible result: an accepted wide/narrow experience contract for Capture → Inbox → context receipt → proposal → canonical scene/Canvas.
  • Entry point: persistent project rail/command path and narrow Capture destination.
  • Successful end state: founder can trace capture, deterministic promotion, agent review, stale refusal, and return to Draft/Canvas without duplicate truth.
  • Refusal/error states: unauthenticated, unsaved/conflicted capture, missing/deleted provider key, disallowed media, failed upload, stale proposal, ambiguous target, revoked grant, and provider outage.
  • Non-goals: product implementation, generic chat, automatic model calls, automatic placement, open-web research, transcription/OCR, external apply, and full import/export.

Parent frame

  • Parent owns product thesis, source-of-truth reconciliation, ADR boundary, checkpoint breakdown, and final acceptance.
  • Read-only audits were fanned out for Write UX gaps, agent architecture, historical blueprint reconciliation, and write-anywhere journey mapping.
  • Future design or implementation delegates must return outcome, files, evidence, parent-owned items, and stop reason.
  • Shared capture/proposal state machines, migrations, and version-domain code remain serial.

Domain map

  • Canonical manuscript: existing SceneId, scene working version, immutable revisions/variants, lease, and recovery remain authoritative.
  • Capture: proposed project-owned noncanonical document with dedicated version/revisions and source modality.
  • Inbox: projection over captures, runs, and proposals rather than a duplicate store.
  • Promotion: exact capture revision + proposal hash + project/scene/Canvas preconditions; atomic all-or-nothing apply.
  • Archive/delete: capture archive/restore required; attachment deletion and account-exit policy remain checkpoint-0 decisions.
  • History/provenance: initiator, provider/model, workflow version, context receipt, source/target revisions, writer decision, and undo path.
  • Guidance: account collaboration preferences, project instructions, and declarative playbooks are versioned inputs, not authorization or executable behavior; publishing profile data remains outside AI context by default.

Design map

  • Mockups 2.0 supplies the one-story-model, Capture/Inbox, unassigned, write-first/storyboard-first, and narrow direction.
  • Mockups 3.0 remains authoritative that Canvas does not silently choose manuscript placement or reading order.
  • Mockups 4.0 supplies the four bounded roles, quiet draft posture, one scene lease, and propose-not-apply invariant.
  • Mockups 5.0 owns the proposed Capture → Inbox → integration journey and makes its wide, narrow, authority, egress, agent-review, and refusal states interactive.
  • The shipped product and accepted ADRs outrank proposal-only design language where they conflict.
  • Checkpoint 0 must define focus return, no-caret-steal readiness, keyboard/screen-reader path, narrow route, reduced motion, save acknowledgement, and stale/recovery behavior.

Binding map

  • Core: new capture, context, run, proposal, credential-policy, instruction-compiler/playbook-policy, and apply services; reuse scene/project/Canvas commands.
  • Storage: memory and Postgres capture/proposal/credential metadata; private object storage for binary attachments.
  • Backend: authenticated capture/Inbox/upload/provider/run/proposal routes with stable errors and server-assembled context.
  • Client/UI: Capture composer, recovery, Inbox, receipt/review/apply, Draft/Canvas handoff, and responsive navigation.
  • Capabilities/MCP: capture/context read and proposal create under server grants; canonical apply remains a first-party exception.

Cumulative coherence gate

  • All success UI follows durable acknowledgement
  • Conflicts apply nothing and expose review/recovery

2026-07-24 — Checkpoint 0 decisions and ADRs accepted

2026-07-24 — Checkpoint 1 implementation frame locked

  • Capture uses its own working version and CAPTURE_VERSION_CONFLICT; it never advances project, scene, or Canvas versions.
  • V1 persists genesis plus integration provenance, not one immutable revision per autosave. Default lists hide archived Captures; an explicit filter includes them.
  • Opening Capture may create an empty acknowledged Capture to keep the composer immediate and recovery identity stable. Untouched empty Captures are omitted from the normal Inbox projection and may be cleaned up later; they never become Scenes.
  • Closing attempts to flush. If acknowledgement fails, the writer may still close with explicit Not saved/recovery truth; no local/server merge occurs.
  • Checkpoint 1 supplies the accepted center-workspace/narrow-route Inbox as a minimal Capture list/open surface. Integration actions remain checkpoint 2.
  • Capture recovery generalizes the existing encrypted document-recovery behavior by entity type and ID. Capture has no editing lease in the owner-only release.
  • The Capture overlay hides background workspace content from assistive technology while open, traps focus, closes on Escape, and restores the invoking focus/selection without unmounting the active Draft.

Development is split serially across core/memory, Postgres/migration, backend API, and client/UI orchestration. One writer owns each shared version domain at a time; the parent reviews every return and owns browser/end-to-end acceptance.

2026-07-24 — Checkpoint 3 mixed-media frame locked

  • Attachment bytes use direct short-lived browser PUT to private R2; Fly authorizes init/finalize/download/delete and never proxies ordinary upload bytes.
  • Upload URLs expire after 15 minutes; download URLs after 5 minutes; pending metadata expires after 24 hours. R2 CORS allows exact trusted production/preview/local origins, PUT/GET/HEAD, signed Content-Type, and exposed ETag.
  • Pending and ready attachments count toward the 10-per-Capture and 200 MiB-per-project quotas. Reservation is transactional so concurrent inits cannot exceed either limit.
  • Finalize re-reads the bounded object through the backend adapter, computes SHA-256, and detects the allowlisted magic/text type before marking ready. It does not trust client MIME, client checksum, ETag, or metadata alone.
  • Images/audio/PDF/plain text retain the accepted 8/15/5 MiB limits. Unsupported, mismatched, oversized, archive, executable, and octet-stream content fails closed and the object is removed or queued for cleanup.
  • Attachment add/finalize requires an editable draft/ready Capture. Authenticated list/download and explicit delete remain available for integrated/archived source review. Delete removes bytes and leaves a metadata tombstone; account exit still retains until explicit purge.
  • Attachments remain parallel Capture metadata. Promotion copies prose only; attachments do not become ProseMirror nodes, scene image references, model context, OCR, or transcription.
  • Image/file picker and recorded audio use the same upload pipeline. Browser dictation remains text at the caret and is not an audio attachment.
